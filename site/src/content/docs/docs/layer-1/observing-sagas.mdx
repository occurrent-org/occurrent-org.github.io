A saga runs for as long as its process does, so sooner or later you need to ask operational questions about one. Is this instance still running, which step is it waiting in, and which instances have stopped moving? `SagaInstance` answers those and nothing else:

<Tabs syncKey="lang">
  <TabItem label="Java">
    ```java
    SagaInstances instances = runningSaga.instances();

    instances.find(orderId).ifPresent(instance ->
            System.out.println(instance.sagaId() + " is " + instance.status() + " in step " + instance.currentStep()));

    // active instances that have not moved for an hour, stalest first
    List<SagaInstance> stalled = instances.findByStatus(SagaStatus.ACTIVE, Instant.now().minus(Duration.ofHours(1)), 50);
    ```
  </TabItem>

  <TabItem label="Kotlin">
    ```kotlin
    val instances = runningSaga.instances()

    instances.find(orderId).ifPresent { instance ->
        println("${instance.sagaId()} is ${instance.status()} in step ${instance.currentStep()}")
    }

    // active instances that have not moved for an hour, stalest first
    val stalled = instances.findByStatus(SagaStatus.ACTIVE, Instant.now().minus(Duration.ofHours(1)), 50)
    ```
  </TabItem>
</Tabs>

`SagaInstances` reads the saga's state store, so it is not the event subscription answering these questions. `SagaSubscription.instances()` is a shortcut that hands you a view over the store the saga already runs against, which is also why it keeps working after you close the handle. Closing stops that instance's timer poller, but it does not close the store. With no handle at hand, in a separate admin process for instance, build one straight from the store with `SagaInstances.of(stateStore)`.

A `SagaInstance` holds:

* the id and the `SagaStatus`
* the created, updated and completed timestamps
* when the next pending timer is due
* which step a flow saga is waiting in
* what the instance is failing on

`currentStep()` is `null` for a core saga, which names its states in your own state type rather than in a step the executor knows about.

The status is `ACTIVE`, `COMPLETED`, or `QUARANTINED`. A quarantined instance stopped on an event it could not handle, so it is neither running nor finished, and [Quarantined Instances](/docs/layer-1/observing-sagas/#quarantined-instances) below says what to do with one.

A `null` from `failure()` means no failure is on record. The instance can still be failing, because these failures record nothing:

* a failing timeout
* a failing event the saga could not route to an instance
* a failing event on a saga with quarantine off, whether you turned it off or the runner switched it off at startup because the subscription model cannot guarantee it holds every event it delivers
* a failing event that has no redelivery key
* an `OutOfMemoryError`
* a failing event the instance already counts as handled
* a failure where the store read or the record write throws, for example a store that can only read an instance together with its state, when that state no longer decodes
* a failure whose record write loses its compare-and-set to another writer

When the store read or the record write throws, or the write loses its compare-and-set, the next failure tries the write again.

On an `ACTIVE` instance a non-null answer means an event has failed at least once and the instance has not been quarantined, which can still be true after the budget has run out. On a `QUARANTINED` one it means the instance stopped there.

It leaves out the saga's own state and the executor's delivery bookkeeping on purpose. A read model shaped for querying belongs in the [Projection DSL](/docs/layer-1/views/), and reaching into a saga's private state from outside ties your code to how that process happens to be written.

There is no way to write through this. Nothing here starts, advances, completes, or deletes an instance, because the executor owns those transitions and a compare-and-set save from outside would race the subscription and the timer poller. Retention tooling that really has to remove an instance calls `SagaStateStore.delete(...)`.

`findByStatus` returns the instances in a status whose `updatedAt` falls strictly before the instant you pass, least recently updated first, at most `limit` of them. Pass `Instant.now()` to list everything in a status, or `Instant.now().minus(threshold)` to find the ones that have gone quiet. Stalest-first is what a stuck-instance check wants, because the worst offenders arrive first rather than last. `limit` caps how many instances you get back, there is no paging. Many instances can share the same millisecond `updatedAt`, and resuming a second query from "after that timestamp" would skip the rest of the instances saved in that same millisecond.

`findByStatus(ACTIVE, ...)` does not return a quarantined instance, so once quarantine is on, a check for instances that have stopped moving has to ask for both statuses. Pass `Instant.now()` for the quarantined query rather than a threshold, because a quarantined instance's `updatedAt` stops at the moment it was quarantined and a threshold would hide the ones quarantined most recently.

Enumeration is an optional store capability. A store implements `SagaStateStoreQueries` to support it, both shipped stores do, and `findByStatus` throws an `UnsupportedOperationException` on a store that does not. `find(sagaId)` works on any store, so a store you wrote yourself to run sagas never has to answer an ordered query it does not need.

Enumerating instances is cheap. Listing flow-saga instances never deserializes their state or received events, so a periodic stuck-instance check costs little even with many instances. Rationale in [ADR 0070](https://github.com/johanhaleby/occurrent/blob/main/doc/architecture/decisions/0070-saga-instance-observation.md).

## Quarantined Instances<HeadingBadge text="Added in 0.34.0" />

Each saga gets one subscription, and that subscription delivers the events for all of its instances. An instance that cannot handle an event keeps failing for as long as your subscription model offers that event again.

Quarantine can end that once the instance has been failing for a length of time you set, and only when the conditions in [What else has to be true](/docs/layer-1/observing-sagas/#what-else-has-to-be-true) hold as well. From 0.35.0 it is on by default, after 5 minutes, and [Configuring quarantine](/docs/layer-1/observing-sagas/#configuring-quarantine) says how to change the budget or turn it off.

When an instance is quarantined, this happens:

* The instance never applies the event it failed on, or any later event addressed to it. Those events still reach the saga, which skips them for this instance without recording them as handled. From 0.35.0 the instance records the key of each event it skips, as a record of its own outside the instance's document, so a release can replay them.
* Its timers stay armed but never fire, so a timeout it relies on to cancel or compensate never runs.
* The other instances of the saga keep getting their events.
* Nothing is deleted. The events stay in the event store, and the instance's state stays in the state store.
* Nothing resumes it on its own. Fixing what made it fail doesn't release it. From 0.35.0 [Releasing a quarantined instance](/docs/layer-1/observing-sagas/#releasing-a-quarantined-instance) brings it back. In 0.34.0 deleting it with `SagaStateStore.delete(sagaId)` is the only way out, and whatever business process the instance was running then has to be finished outside the saga.

Before an instance is quarantined, or when quarantine is off, [Delivery Contract](/docs/layer-1/saga-delivery/) says which other events wait behind the failing one.

This lists the quarantined instances of a saga and what each one stopped on:

<Tabs syncKey="lang">
  <TabItem label="Java">
    ```java
    List<SagaInstance> stopped = instances.findByStatus(SagaStatus.QUARANTINED, Instant.now(), 50);

    for (SagaInstance instance : stopped) {
        SagaFailure failure = instance.failure();
        System.out.println(instance.sagaId() + " stopped on " + failure.input() + " with " + failure.failureType());
    }
    ```
  </TabItem>

  <TabItem label="Kotlin">
    ```kotlin
    val stopped = instances.findByStatus(SagaStatus.QUARANTINED, Instant.now(), 50)

    for (instance in stopped) {
        val failure = instance.failure()
        println("${instance.sagaId()} stopped on ${failure?.input()} with ${failure?.failureType()}")
    }
    ```
  </TabItem>
</Tabs>

`SpringMongoSagaStateStore` stores an instance that 0.35.0 quarantined with the status `QUARANTINED_RECORDING`, and one that 0.34.0 quarantined with `QUARANTINED`. Both read back as `SagaStatus.QUARANTINED`, and `findByStatus` matches both. A MongoDB query you write by hand has to match both strings, `{ status: { $in: ["QUARANTINED", "QUARANTINED_RECORDING"] } }`.

### The failure record and the quarantine budget

`failure()` holds the failing event's redelivery key, its global position where the feed assigns one, the exception's class name and message, and `firstFailedAt`, the time the instance's first failure was recorded. A message longer than 1,000 characters is cut short in the record, and the log still has the whole exception.

The runner measures how long the instance has been failing, not how many times it failed. The budget is `SagaRunnerConfig.quarantineAfter`, measured from `firstFailedAt`.

An instance's first failure writes the failure record and is then rethrown, whether or not the write succeeded, so a subscription model that offers the event again lets the saga try again. An event that fails before its instance exists creates the instance to hold the record.

That first write happens only for a failure that could be quarantined later, and [Observing Saga Instances](/docs/layer-1/observing-sagas/) lists the failures that record nothing. When nothing was recorded, the next failure is treated as a first failure again.

The same event failing again inside the budget writes nothing more. A different event failing rewrites the record to name that event and keeps `firstFailedAt`. The budget is still measured from `firstFailedAt`, so the instance can be quarantined on the new event's first failure.

Once the instance has been failing for at least the budget, the next failure can move it to `SagaStatus.QUARANTINED` on whichever event it is failing on then. When it does, the runner returns normally instead of rethrowing. The instance never applies that event or any later one of its own, and the other instances of the saga move on to their next events.

Reaching the budget does not quarantine an instance on its own, so an instance past its budget can still be `ACTIVE`. Read its status instead of working it out from the time.

When the event the record names later succeeds, the record is cleared. A different input succeeding does not clear it.

Every way of failing counts once the saga knows which instance the event belongs to. Checking for a redelivery, `evolve`, `react`, your command dispatcher and the state store all do, and an `Error` counts like a `RuntimeException`. The exception is `OutOfMemoryError`. It means the JVM ran out of heap while that instance happened to hold the thread, so the runner rethrows it and the instance keeps its state.

A short MongoDB outage never reaches the runner as a failure. `SpringMongoSagaStateStore` retries every read and write it makes, backing off from 100 ms up to 2 seconds and giving up after ten attempts, so a database that answers again before those run out is not a failure at all. A longer outage does count, but the quarantine is written to that same database, so it quarantines nothing while the outage lasts.

Pass your own [RetryStrategy](/docs/stores/retry/#retry-configuration-blocking) to the store's five-argument constructor to change that, or `RetryStrategy.none()` to have every failure reach the runner on the first attempt. A `@Saga` that declares no store of its own gets the default, since the Spring Boot starter builds the store the same way.

An event the saga cannot route to an instance stops no instance at all. [Delivery Contract](/docs/layer-1/saga-delivery/) says what happens to it.

### Quarantine on a `SagaStateStore` of your own

A `SagaStateStore` never sees a `SagaEnvelope`. `SagaCodec` turns each instance into a `StoredSaga`, which holds the saga id, the version, the encoded fields and a `SagaIndex` with the values the store queries on, and the store persists it as it is. A store decides only how a core saga's state is represented, and returns that as a `SagaStateCodec` from `stateCodec()`.

Two of its members let the runner quarantine an instance whose state can no longer be decoded, which is what a renamed event class or a changed converter produces. That instance is very often the one you most want quarantined, since it fails on every event addressed to it.

`findWithoutState(sagaId)` reads an instance without its state. It needs only the fields in `SagaCodec.fieldsWithoutState()`, and the runner ignores the state when the read returns one.

`compareAndSaveWithoutState(saga, expectedVersion)` writes an instance back under the same compare-and-set rule as `compareAndSave`. It sets the fields in `SagaCodec.fieldsExceptState()` from the `StoredSaga`, removes the ones the `StoredSaga` has no value for, and keeps the stored state as it is, so the state the instance stopped on is still there for whoever repairs the converter. It throws an `IllegalArgumentException` for an `expectedVersion` of 0, since the runner inserts with `compareAndSave`.

Neither has a default. `SagaStateStore.inMemory()` and `SpringMongoSagaStateStore` implement both, and the [0.35.0 upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.35.0.md#a-sagastatestore-stores-an-encoded-saga) walks through porting a store of your own. `SagaInstances.find(sagaId)` uses `findWithoutState` too, so looking one instance up by id costs the same as enumerating them and also works for an instance whose state no longer decodes.

### What else has to be true

An instance past its budget is quarantined only when a few other conditions are met too. The next three sections cover the ones you're most likely to run into, and the javadoc on `SagaStatus.QUARANTINED` lists every one.

### Use a subscription model that keeps every event

Quarantine only works on a subscription model that keeps every event it delivers. A model says it does by implementing `HistoryRetainingSubscriptions` and returning `true` from `retainsEveryEvent()`.

Quarantining an instance returns normally, which acknowledges the event to whatever fed it. Behind a broker source, the source then acknowledges the record to the broker, and nothing can hand that event to the saga a second time.

`NativeMongoSubscriptionModel` and `SpringMongoSubscriptionModel` return `true`, either of them alone or behind `DurableSubscriptionModel`, `CompetingConsumerSubscriptionModel` or `CatchupSubscriptionModel`. The runner looks through those three wrappers to the model inside, so a wrapper around any other model doesn't qualify.

`CatchupThenPushSubscriptionModel` implements `HistoryRetainingSubscriptions` but returns `false` from `retainsEveryEvent()`, since the live events pushed to it need not be in the event store it replays. A push feed on its own does not implement the interface at all.

When you turn quarantine on for a saga on a model that returns `false` from `retainsEveryEvent()`, or doesn't implement `HistoryRetainingSubscriptions`, the runner switches it off again at startup and logs a `WARN` saying why. An instance that keeps failing on such a model is never quarantined.

### An event without a redelivery key is never quarantined

The failure record identifies the failing event by its redelivery key, the stream id with its stream version, or the global position when the event has no stream metadata. An event with neither can't be told apart from its own redelivery, so its budget never runs out and it is never quarantined.

`SagaRunnerConfig.redeliveryDetection` refuses such an event under `REQUIRED`, its default, before the saga sees it. You only meet this case after setting it to `BEST_EFFORT`.

An event store that assigns no global position still gives every event a redelivery key. A store built with `withoutStreamPosition()` gives every event a stream id and a stream version, so a saga on it quarantines like any other and `failure().position()` returns `null`.

### The runner checks that the model still holds the event

Before the runner quarantines an instance, it calls the model's `retains(event)` for the event the instance stopped on. `retains` returns `true` when acknowledging the event doesn't delete the only copy of it. A model that returns `true` from `retainsEveryEvent()` by mistake is caught this way, before the event is gone.

When `retains` returns `false`, or throws, the instance isn't quarantined. The runner logs a `WARN` once per instance, and the instance keeps failing for as long as your model offers the event again.

An event an operator has already deleted from the event store isn't deleted by the acknowledgement, so `retains` returns `true` for it. The instance can then be quarantined, so it doesn't keep failing on an event nobody can supply.

### Configuring quarantine

From 0.35.0 `SagaRunnerConfig.defaults()` quarantines an instance once one event has kept failing for 5 minutes. In 0.34.0 quarantine is off by default, because nothing there brings a quarantined instance back. The 3- and 4-argument `SagaRunnerConfig` constructors never quarantine.

Pass another budget to `withQuarantineAfter`, or turn quarantine off with `disableQuarantine()`:

<Tabs syncKey="lang">
  <TabItem label="Java">
    ```java
    SagaRunnerConfig longer = SagaRunnerConfig.defaults().withQuarantineAfter(Duration.ofMinutes(30));
    SagaRunnerConfig off = SagaRunnerConfig.defaults().disableQuarantine();
    ```
  </TabItem>

  <TabItem label="Kotlin">
    ```kotlin
    val longer = SagaRunnerConfig.defaults().withQuarantineAfter(Duration.ofMinutes(30))
    val off = SagaRunnerConfig.defaults().disableQuarantine()
    ```
  </TabItem>
</Tabs>

`withQuarantineAfter(null)` throws, and so does a zero or negative budget.

With quarantine off, the saga keeps refusing a failing instance's event for as long as your subscription model offers it again. On the MongoDB subscription models the saga's other instances wait behind that event the whole time.

On a model that keeps every event, `SagaRunner.run` throws an `IllegalStateException` when quarantine is on and the runner has no `EventStoreQueries`, since a release reads the skipped events back with it. That holds for the defaults and for a budget you set yourself. The message says to pass the event store with `SagaRunner.eventStoreQueries(..)`, since every blocking event store Occurrent ships implements `EventStoreQueries`, or to turn quarantine off with `disableQuarantine()`.

While an instance is quarantined it records the key of every event it skips, as a record of its own outside the instance's document, so a quarantine can record any number of events. On MongoDB the records are documents in a collection named after the saga collection with `_skipped_inputs` appended, one per skipped event, each with `sagaId`, `quarantineId`, `seq` and `key`. `SpringMongoSagaStateStore` therefore throws an `IllegalArgumentException` for a saga collection whose name ends in `_skipped_inputs`, since a store on the name without that suffix would keep its skipped events there.

### Releasing a quarantined instance<HeadingBadge text="Added in 0.35.0" />

`SagaSubscription.release(sagaId)` reads the event the instance stopped on from the event store and applies it the way a delivery is applied, and then does the same for each event the instance skipped, in the order they arrived. The instance stays `QUARANTINED` while that runs and becomes `ACTIVE` once no recorded event is left, so an event that arrives during the release is recorded and replayed too. A release dispatches the commands those events produce.

A timer that came due while the instance was quarantined fires after every recorded event has been replayed, including events that arrived after its deadline, because a saga's timers run on processing time. For a saga that uses a timer as a deadline, a replayed event from after the deadline that cancels or re-arms the timer means the timeout never fires.

<Tabs syncKey="lang">
  <TabItem label="Java">
    ```java
    SagaSubscription.ReleaseResult result = runningSaga.release(orderId);
    ```
  </TabItem>

  <TabItem label="Kotlin">
    ```kotlin
    val result = runningSaga.release(orderId)
    ```
  </TabItem>
</Tabs>

It takes no lease and pauses nothing, so you can call it on any node. It returns one of these:

* `RELEASED`. The instance replayed every event and is `ACTIVE`, or `COMPLETED` when one of them completed it.
* `STILL_RELEASING`. An event failed again, and the instance stays releasing.
* `QUARANTINED_AGAIN`. An event kept failing during the release until its budget ran out, or the event store handed back an event without a stream id and stream version, which only an `EventStoreQueries` other than Occurrent's own event stores can do. The instance is quarantined on that event, which stays recorded with the events after it, so a later release starts from it.
* `QUARANTINED_EVENT_MISSING`. The event store no longer has one of the events. The instance is quarantined on it at once, with `EventMissingFromStore` as its `failureType()`, and the event stays recorded, so the next release starts from it. Restore the event and release again, or delete the instance.
* `NOT_QUARANTINED` or `NOT_FOUND`. There was nothing to release.

The timer poller goes on with every instance that is releasing after each poll, so it retries an event that failed during a release and resumes a release a crash interrupted. With a competing-consumer strategy only the node holding the saga's timer lease does that. Calling `release` again goes on where the release stands too. One poll replays at most `timerBatchLimit` events, 100 by default, shared evenly among the releasing instances it lists, at least one each, and the next poll goes on where the last one stopped. A `release` call has no such bound. The event the instance stopped on gets a full quarantine budget again, measured from the start of the release.

A release reads the events with an `EventStoreQueries`, which you give the runner with `SagaRunner.eventStoreQueries(..)`. Without one, `release` throws an `IllegalStateException`. It also throws one for an instance that 0.34.0 quarantined, since that instance has no record of what it skipped, and deleting it with `SagaStateStore.delete(sagaId)` is what's left. It throws one for an instance whose state no longer decodes too, with a message that names the decoding failure. Fix how the state decodes and release it again, or delete it. An instance whose state stops decoding while it is releasing stays releasing, and each poll logs a `WARN` and tries again.

A `SagaStateStore` of your own implements `SagaStateStoreSkippedInputs` for a release. It keeps the skipped events with `recordSkippedInput`, `findSkippedInputs`, `deleteSkippedInput`, `deleteSkippedInputByKey` and `deleteSkippedInputs(sagaId, quarantineId)`, deletes the records of the removed instance's quarantine id in `delete(sagaId)`, and implements `findReleasingSagaIds(after, limit)` for the poller to go on with a release.

The design is in [ADR 0134](https://github.com/johanhaleby/occurrent/blob/main/doc/architecture/decisions/0134-a-saga-instance-that-keeps-failing-is-quarantined-at-its-own-position.md) and [ADR 0178](https://github.com/johanhaleby/occurrent/blob/main/doc/architecture/decisions/0178-a-quarantined-saga-instance-records-what-it-skips-and-is-released-by-replaying-it.md). The [quarantined saga instance runbook](https://github.com/johanhaleby/occurrent/blob/main/doc/runbooks/quarantined-saga-instance.md) walks through a release step by step.

:::tip[Using Spring Boot?]
The `@Saga` registrar publishes a `SagaInstancesRegistry` bean, and each saga's `SagaSubscription` as `sagaSubscription-<id>`, which is what you call `release` on. `occurrent.saga.quarantine-after` sets the budget, which is 5 minutes when it is left out or blank, and `occurrent.saga.quarantine-enabled=false` turns quarantine off. With quarantine on, several `EventStoreQueries` beans and none of them `@Primary` fail at startup. See [Observing @Saga instances](/docs/spring-boot/saga-annotation/#observing-saga-instances).
:::
