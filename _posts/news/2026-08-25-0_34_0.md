Occurrent 0.34.0 is released. It can forward stored events to RabbitMQ or Kafka and consume them back into a push subscription, and it removes the flow saga's deprecated `join`. Below are five highlights, a few smaller additions, and eleven changes to read before you upgrade.

## Highlights

### Forward events to RabbitMQ or Kafka

The new `occurrent-broker-api-blocking` module forwards stored events to a broker at least once. `CloudEventForwarder` runs a durable subscription and hands each stored event to a `CloudEventSink`, and it saves the checkpoint only once the sink has returned. If the sink throws, the same event is published again on the next run. `DomainEventForwarder` does the same for an application whose converter already produces domain events.

`occurrent-broker-rabbitmq-blocking` and `occurrent-broker-kafka-blocking` each ship a sink and a bridge. The sink is the publish side. A RabbitMQ publish returns only once the message is both confirmed and routed, and a Kafka publish only once the broker has acknowledged it with `acks=all`. The bridge consumes messages back into a `PushSubscriptionModel` or a `DomainEventFeed`.

With Spring Boot, `@EnableOccurrentRabbitMqBroker` or `@EnableOccurrentKafkaBroker` builds the sink and a bridge factory from `occurrent.broker.rabbitmq.*` or `occurrent.broker.kafka.*`. The broker modules are blocking only. [The documentation](/documentation#broker-subscriptions-blocking) shows the wiring for each broker, and `example/broker/rabbitmq` in the Occurrent repository runs the whole loop against RabbitMQ and MongoDB.

### Sealed event types expand everywhere

Declare a sealed event supertype and it now matches every concrete type it permits. That holds for projections, subscriptions built through the subscription DSL, queries through `DomainEventQueries`, `@Snapshot` views, `ExecuteFilter`'s `type` and `includeTypes`, and `DcbCriteriaBuilder`'s `type` and `types`. A saga and an annotation-based subscription already worked this way.

`ExecuteFilter.excludeTypes` goes one step further. A declared type it cannot fully expand is widened to every concrete subtype it can find, because excluding a supertype has to exclude everything under it.

[The documentation](/documentation#deriving-the-event-filter) says how a declared type becomes a filter. See the breaking change below for what happens when a declared type cannot be expanded.

### PushSubscriptionModel gets an observation hook

`PushSubscriptionModel` takes an optional `PushObserver`. Once per event, the observer is told how that event was routed, as a `RoutingOutcome` rather than a boolean. It lives in the core library, so it works with or without Spring Boot, and the reactive model takes the same observer.

`DELIVERED` and `FILTERED` both mean a running subscription looked at the event and answered for itself, by accepting it or by declining it under its filter. The other four, `UNAVAILABLE`, `NOT_DELIVERABLE`, `DEFERRED` and `REFUSED`, each say something different about why nothing consumed it, and each one calls for a different response.

If you acknowledge broker messages, `outcome.mayAcknowledge()` tells you whether you may, true for `DELIVERED` once `accept(..)` has returned normally and for `FILTERED`, false for the other four. `outcome.disposition()` gives the fuller answer, one of `ACKNOWLEDGE`, `HOLD`, `FAIL` or `STOP`, so a bridge you write switches on four values rather than on six outcomes. That is what makes a misconfigured queue binding or a type-mapping typo visible instead of silent, and [the documentation](/documentation#push-subscription-blocking-observer) says what each outcome means.

The RabbitMQ and Kafka bridges above are built on it. They acknowledge on `DELIVERED` and `FILTERED`, hold `DEFERRED` and `UNAVAILABLE` for redelivery, apply your `DeliveryFailurePolicy` to `NOT_DELIVERABLE`, and stop on `REFUSED`.

### A saga instance that keeps failing can be quarantined

Up to 0.33.0, an event a saga's `evolve`, `react` or command dispatcher could not handle failed its instance on every delivery, with no limit. Now an instance that has kept failing for longer than `SagaRunnerConfig.quarantineAfter`, five minutes by default, can move to `SagaStatus.QUARANTINED`. A quarantined instance stops receiving events and stops firing timers.

With Spring Boot the budget is `occurrent.saga.quarantine-after`. A saga fed by a push source is never quarantined, and it logs a warning at startup saying so.

[The documentation](/documentation#saga-quarantined-instances) covers how to find a quarantined instance, and the [runbook](https://github.com/johanhaleby/occurrent/blob/main/doc/runbooks/quarantined-saga-instance.md) walks through deciding what to do with one.

### An asynchronous projection can wait for its own write

Every write and DCB append now returns an `AppendId`, and a projection can record which ones it has applied. Wait for a specific append with `AppliedAppendStore.waitUntilApplied(...)` instead of running the whole projection synchronously just to see your own write.

With the Spring Boot starter, set `recordAppliedAppends = true` on `@Projection` and the store and the recording are wired for you. Without Spring Boot you wrap the view with `Projections.recordingAppliedAppends(..)`, register the wrapper for catch-up, and call `pollForClear()` on a schedule of your own.

See [the documentation](/documentation#projection-annotation-applied-appends) for the worked example and what the wait does and doesn't guarantee.

### Smaller additions

- `Projection.builder()`, `Projection.singletonBuilder()`, `Saga.builder()` and `SnapshotView.builder()` gain a no-argument overload for state that starts empty, and `View.create` gains one too, so you no longer pass `null`. In Kotlin the state is then `S?`, so a handler that uses it without a null check fails to compile instead of throwing on the first event.
- `@Transactional`, or any other Spring aspect, on a `@Subscription`, `@StreamSubscription`, `@DcbSubscription` or `@SynchronousSubscription` handler method now applies to every delivery, including one delivered while Spring Boot is still starting.
- `SpringMongoSagaStateStore` retries a transient MongoDB error, with backoff from 100 ms up to 2 seconds and at most 10 attempts. An error a second attempt would have cleared no longer reaches the saga as a failed transition, so it no longer counts toward quarantine.
- A `@Projection`, `@Saga` or `@Snapshot` on a bean Spring Boot builds only after startup, a `@Lazy` bean for example, now registers when the bean is built. In 0.33.0 it never registered.
- `ReactorMongoEventStore.updateEvent` no longer logs the whole stored document, data payload included, at INFO.

## Breaking changes

### The flow saga's `join` is removed

The flow saga's deprecated `join`, Kotlin's `expect<T>`, and `Expectation` are gone. That is the saga DSL itself, so it affects you whether or not you run Spring Boot.

`join` was already deprecated in 0.33.0 in favor of `on(StepCondition, ...)` with `allOf(...)`, and that replacement is what every caller now needs.

The `org.occurrent.UpgradeToOccurrent_0_34` recipe rewrites a `join` call built from a literal list of literal `Expectation.of(...)` calls to `on(allOf(...))`. A list built from a variable or a method call, and every Kotlin call site, are left alone and stop compiling, so the compiler finds them for you.

### A flow saga's `stepWindow` now caps its declared events and the start type

`stepWindow` counts and evicts only events of a type one of the flow's own steps names, in an `on(...)` branch or in an `event(...)` check inside a window condition, plus an event of the type that starts the flow. An event of any other type is still kept, it just no longer takes a slot from the cap or evicts a declared event to make room for itself.

This reaches you only if your flow sets a `narrowingFilter`, sets a `replacementFilter` wider than its own declared types, or uses a `CloudEventTypeMapper` that maps several domain types onto one CloudEvent type string. `stepWindow` now puts no limit at all on a step fed only events of a type no step declares, so watch the store-boundary warning if your flow admits those and you care about document size. [Section 2 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#2-a-flow-sagas-stepwindow-now-caps-its-declared-events-and-the-start-type) has the rest.

### An event type whose concrete subtypes cannot be found is refused

A projection, a subscription built through the subscription DSL, a query through `DomainEventQueries`, a `@Snapshot` view, `ExecuteFilter`'s `type` and `includeTypes`, and `DcbCriteriaBuilder`'s `type` and `types` now refuse a declared event type whose concrete subtypes cannot be found. A saga and an annotation-based subscription already refused it in 0.33.0.

A concrete class that is neither final nor sealed used to be accepted everywhere, and it is now refused as well, by a saga and an annotation-based subscription too. A subclass of such a class is stored under its own CloudEvent type, so it never reached a handler declared on the parent, and nothing said why.

`ExecuteFilter.excludeTypes` now refuses an array or a primitive declared type, which it accepted up to 0.33.0.

Seal the hierarchy, mark the class `final` when nothing extends it, or declare the concrete event types. Where one is available, an explicit filter works too. [Section 3 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#3-declaring-an-event-type-whose-concrete-subtypes-cannot-be-found-is-refused) has a table of every refused declaration.

### Four MongoDB-only config keys move under `mongodb`

The rename only reaches you if you configure Occurrent through Spring Boot properties. `occurrent.event-store.collection`, `occurrent.event-store.time-representation`, `occurrent.subscription.collection` and `occurrent.subscription.restart-on-change-stream-history-lost` are renamed to their `mongodb`-qualified equivalents.

Each old key still works and is deprecated, and it will be removed in the release after next. Setting both the old and the new key to different values fails startup with an error that names both.

The `UpgradeToOccurrent_0_34` recipe rewrites both `.properties` and `.yaml` for you. It cannot see an environment variable such as `OCCURRENT_EVENT_STORE_COLLECTION`, so rename those by hand. [Section 4 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#4-four-mongodb-only-keys-move-under-mongodb) lists the new keys.

### A descriptor factory's class-level advice no longer runs at startup

This only happens in the Spring Boot integration. A `@Projection`, `@Saga` or `@Snapshot` bean's class-level advice, `@Transactional` or a custom aspect for example, no longer runs once at startup as a side effect of its descriptor factory being invoked. That was never documented behavior, just an accident of CGLIB proxying the bean under the default `spring.aop.proxy-target-class=true`.

A reactor factory that returns `null` also now fails startup with `IllegalStateException` instead of `IllegalArgumentException`, matching what the blocking stack already threw for the same mistake.

### `WriteResult` and `DcbAppendResult` gain a fourth component

Both records gain `Optional<AppendId> appendId()`, which is the identifier behind the highlight above. Two things break and only one of them is a compile error.

A record pattern naming the original three components stops compiling, and the recipe appends the fourth binding for you.

An assertion comparing a whole record, `assertThat(result).isEqualTo(new WriteResult(streamId, 0, 1))`, still compiles. It now fails when it runs, because a fresh append id is generated for every write that persists something, and nothing at build time points at it. No recipe can reach it either, since the expected append id is a value your source never states. Assert on the components you actually mean instead. [Section 6 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#6-writeresult-and-dcbappendresult-gain-a-fourth-component-the-append-id) has the before and after.

### `DurableSubscriptionModel` refuses a first subscription when no start position can be recorded

`DurableSubscriptionModel.subscribe(..)` now throws `IllegalStateException` when you ask for the default start position, no checkpoint is stored for the subscription id, and the wrapped model cannot say where the feed is. Both MongoDB models answer that way when the server refuses the `hostInfo` command, which shared Atlas clusters (M0, Flex and similar tiers) do. In a Spring Boot application it comes out as a startup failure.

The old behavior was that such a subscription started anyway from wherever the feed happened to be, with nothing recorded, so a crash before the first checkpoint was saved never came back to the event whose delivery had just failed. The refusal replaces that quiet loss with an error.

There are three ways forward:

- Set `occurrent.subscription.start-when-no-start-position-can-be-recorded=true`, or `DurableSubscriptionModelConfig.startWhenNoStartPositionCanBeRecorded(true)` without Spring Boot. You get the old behavior, chosen deliberately this time.
- Run against a tier that permits `hostInfo`, which on Atlas means M10 and up. The subscription then records its start position before anything is delivered.
- Subscribe with a `StartAt` of your own.

[Section 7 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#7-durablesubscriptionmodel-refuses-a-first-subscription-when-no-start-position-can-be-recorded) covers what each one costs.

### Four saga types change for quarantine

The quarantine in the highlights above changes the saga API in five ways. `SagaStatus.QUARANTINED` is a new constant, so an exhaustive `switch` or `when` over `SagaStatus` stops compiling. `SagaInstance` gains `failure()`, `SagaEnvelope` gains a `started` and a `failure` component, and `SagaRunnerConfig` gains `quarantineAfter`, each of which breaks a store, an implementation, or a record pattern written against 0.33.0.

The fifth breaks nothing at compile time. `findByStatus(ACTIVE, ...)` no longer returns a quarantined instance, so a stuck-instance check built on it now misses the instances that have stopped for good. Enumerate `QUARANTINED` as well. There is no recipe for any of the five. [Section 8 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#8-a-saga-instance-that-keeps-failing-is-quarantined-and-four-saga-types-change-with-it) has the code.

### A reactor catch-up subscription can deliver a concurrent write twice

A reactor catch-up subscription now delivers an event a second time when a write that was still in flight during the replay was read by a history window. The replay used to put every id it read into the cache the live delivery filters against, so the change stream's own delivery of that event was dropped. The history reads now fill no cache, which is what all three blocking paths already did.

This is `ReactorStreamCatchupSubscriptionModel`, `ReactorDcbCatchupSubscriptionModel`, and `ReactorCatchupSubscriptionModel`, which routes to them. The blocking catch-up models are unchanged, and a store with nothing being written during the replay sees no repeats at all.

Catch-up delivery on these models has always been at-least-once, so a handler that already tolerates a repeat needs no change. If yours increments a counter or writes an unconditional insert, make it safe before you upgrade, usually by keying the work on the CloudEvent id. `handoverCacheSize` now sizes the reconciliation overlap alone rather than the whole replay, so a value you raised for a large rebuild is bigger than it needs to be. [Section 9 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#9-a-reactor-catch-up-subscription-can-deliver-a-concurrent-write-twice) covers the deployments where the repeats reach further back than concurrent writes.

### Events `updateEvent` damaged before 0.34.0 need a one-off repair

This is stored data rather than code, and it reaches you only if your application called `EventStoreOperations.updateEvent` while running 0.33.0 or earlier. That write path stored `position` as a string instead of a number and dropped the indexed `dcbTags` array. 0.34.0 fixes the write path. It does not repair events that are already stored.

MongoDB compares values within a type, so a string `position` matches neither end of a numeric range. A damaged event is missing from DCB reads, from `exists` and `count`, from position-ordered stream reads, from position-based catch-up, and from the conflict query behind a conditional append, where it means an append that should have been refused is accepted. Nothing raises an error at any point. The position half of this hits a store with stream position enabled even if it never used DCB.

A store that writes `position` now looks for a string `position` when it starts and logs a warning when it finds one. That check sees nothing else, so a quiet startup does not prove the store is clean. Set `EventStoreConfig.Builder.requireRepairedEvents(true)` if you would rather the store refused to start.

Run the `occurrent-eventstore-mongodb-update-event-repair` module to fix what it finds. Read [the documentation](/documentation#update-event-repair) or [section 10 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#10-events-updateevent-damaged-before-0340-need-a-one-off-repair) first, because some damaged events cannot be restored and the repair reports those by `_id` instead.

### A subscription handler Spring cannot invoke now fails startup

A `@Subscription`, `@StreamSubscription`, `@DcbSubscription` or `@SynchronousSubscription` handler method that Spring's proxy cannot invoke now fails startup with `SubscriptionHandlerNotInvocableException`. Before, it ran on the raw bean with no advice, so `@Transactional` was silently skipped on every delivery. A private or final method behind a CGLIB proxy, a method only the concrete class declares behind a JDK interface proxy, and any static method all hit the check.

These handlers also register later, once every singleton exists, the same phase `@Projection`, `@Saga` and `@Snapshot` use. A subscription starting at `StartPosition.NOW`, and every `@SynchronousSubscription`, therefore never sees an event a bean writes during singleton construction, from its `@PostConstruct` for example. Move that write to an `ApplicationRunner`, or start the subscription at `StartPosition.BEGINNING`. [Section 11 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#11-a-subscription-handler-spring-cannot-invoke-now-fails-startup-and-a-live-subscription-can-miss-a-startup-write) has the details.

Full details are in the [changelog](https://github.com/johanhaleby/occurrent/blob/main/changelog.md), and the [upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md) walks through every change with the by-hand translation where the recipe cannot reach.
