Occurrent 0.34.0 is released. It comes with five highlights, and eleven breaking changes to read before you upgrade.

## Highlights

### Stored events can be forwarded to a broker and consumed back

Occurrent can now forward stored events to a broker. `CloudEventForwarder` runs a durable subscription and hands each stored event to a `CloudEventSink`, and it moves its checkpoint only once the sink has returned, so an event whose publish failed is published again on the next run.

Write the sink yourself, or use the new RabbitMQ and Kafka modules, which also consume from the broker back into a push subscription or a projection. Each of their bridges acknowledges a message only when the event was actually handled, and each broker has a Spring Boot starter too. See [the documentation](/documentation#broker-subscriptions-blocking) for the wiring.

### Sealed event types expand everywhere

Declare a sealed event supertype and it now matches every concrete type it permits. That holds for projections, for subscriptions built through the subscription DSL, for queries through `DomainEventQueries`, and for `ExecuteFilter` and `DcbCriteriaBuilder`, none of which need Spring Boot, and for `@Snapshot` views if you use the Spring Boot starter.

A saga already worked this way. See the breaking change below for what happens when a declared type cannot be expanded.

### PushSubscriptionModel gets an observation hook

`PushSubscriptionModel` takes an optional `PushObserver`. For each event `accept(..)` is asked to deliver, the observer is told how it was routed, as a `RoutingOutcome` rather than a boolean. That makes a misconfigured queue binding or a type-mapping typo visible instead of silent. It needs no Spring Boot, and the reactive `PushSubscriptionModel` takes a `PushObserver` of its own.

`DELIVERED` and `FILTERED` both mean a running subscription looked at the event and answered for itself, by accepting it or by declining it under its filter. The other four, `UNAVAILABLE`, `NOT_DELIVERABLE`, `DEFERRED` and `REFUSED`, each say something different about why the event didn't reach a handler.

If you acknowledge broker messages, `outcome.mayAcknowledge()` is true for `DELIVERED` and `FILTERED` and false for the other four. A handler that threw still reports `DELIVERED`, so acknowledge only once `accept(..)` has also returned normally. `outcome.disposition()` sorts the six outcomes into `ACKNOWLEDGE`, `HOLD`, `FAIL` or `STOP`, so a bridge you write switches on four values. `DEFERRED` and `UNAVAILABLE` both mean hold the message and offer it again later. [The documentation](/documentation#push-subscription-blocking-observer) says what each outcome means.

### An asynchronous projection can wait for its own write

Every write and DCB append now returns an append id, as an `Optional<AppendId>` on its result, and a projection can record which ones it has applied. Wait for a specific append with `AppliedAppendStore.waitUntilApplied(...)` instead of running the whole projection synchronously just to see your own write.

With the Spring Boot starter, set `recordAppliedAppends = true` on `@Projection` and the store and the recording are wired for you. Without Spring Boot, wrap the projection's view with `Projections.recordingAppliedAppends(..)`, register the wrapper with `listenForCatchup` on your subscription model before you subscribe, and call its `pollForClear()` on a schedule.

See [the documentation](/documentation#projection-annotation-applied-appends) for the worked example and what the wait does and doesn't guarantee.

### The deprecated `join` is gone, with a recipe for the mechanical part

The flow saga's deprecated `join` is removed. The new `org.occurrent.UpgradeToOccurrent_0_34` recipe rewrites the mechanical call sites to `on(allOf(...))` for you. See the breaking change below for what the recipe cannot reach.

## Breaking changes

### The flow saga's `join` is removed

The flow saga's deprecated `join`, Kotlin's `expect<T>`, and `Expectation` are gone. That is the saga DSL itself, so it affects you whether or not you run Spring Boot.

`join` was already deprecated in 0.33.0 in favor of `on(StepCondition, ...)` with `allOf(...)`, and that replacement is what every caller now needs.

The `UpgradeToOccurrent_0_34` recipe rewrites a `join` call built from a literal list of literal `Expectation.of(...)` calls. A list built from a variable or a method call, a pair of expectations for the same type whose count is not a literal, and every Kotlin call site are left alone and stop compiling, so the compiler finds them for you.

### A flow saga's `stepWindow` now caps its declared events and the start type

`stepWindow` counts and evicts only events of a type one of the flow's own steps names, in an `on(...)` branch or in an `event(...)` check inside a window condition, plus events of the type that starts the flow. An event of any other type is still kept, it just no longer takes a slot from the cap or evicts a declared event to make room for itself.

This reaches you only if your flow sets a `narrowingFilter`, sets a `replacementFilter` wider than its own declared types, or uses a `CloudEventTypeMapper` that maps several domain types onto one CloudEvent type string. `stepWindow` now puts no limit at all on a step fed only events of a type no step declares and that doesn't start the flow, so watch the store-boundary warning if your flow admits those and you care about document size. [Section 2 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#2-a-flow-sagas-stepwindow-now-caps-its-declared-events-and-the-start-type) has the rest.

### A supertype event declaration is now refused everywhere

Declaring an event type whose concrete subtypes cannot be found is now refused in a projection, in a subscription built through the subscription DSL, in a query through `DomainEventQueries`, in a `@Snapshot` view, in `ExecuteFilter`'s `type` and `includeTypes`, and in `DcbCriteriaBuilder`'s `type` and `types`. 0.33.0 already refused it for a saga and for an annotation-based subscription.

This refusal is also stricter than the one 0.33.0 shipped. A concrete class that is neither final nor sealed used to be accepted everywhere, and it is now refused everywhere, a saga and an annotation-based subscription included. `ExecuteFilter.excludeTypes` widens a supertype rather than refusing it, but it now refuses an array or a primitive type.

Mark the class `final` if nothing extends it, seal the hierarchy, or declare the concrete event types to fix it, or set an explicit filter where one is available. [Section 3 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#3-declaring-an-event-type-whose-concrete-subtypes-cannot-be-found-is-refused) has the error each place throws and its way out.

### Four MongoDB-only config keys move under `mongodb`

The rename only reaches you if you configure Occurrent through Spring Boot properties. `occurrent.event-store.collection`, `occurrent.event-store.time-representation`, `occurrent.subscription.collection` and `occurrent.subscription.restart-on-change-stream-history-lost` are renamed to their `mongodb`-qualified equivalents.

Each old key still works and is deprecated, and it will be removed in the release after next. The new recipe rewrites both `.properties` and `.yaml` for you.

### A descriptor factory's class-level advice no longer runs at startup

This only happens in the Spring Boot integration. A `@Projection`, `@Saga` or `@Snapshot` bean's class-level advice, `@Transactional` or a custom aspect for example, no longer runs once at startup as a side effect of its descriptor factory being invoked. That was never documented behavior, just an accident of CGLIB proxying the bean under the default `spring.aop.proxy-target-class=true`.

A reactor factory that returns `null` also now fails startup with `IllegalStateException` instead of `IllegalArgumentException`, matching what the blocking stack already threw for the same mistake.

### `WriteResult` and `DcbAppendResult` gain a fourth component

Both records gain `Optional<AppendId> appendId()`, which is the identifier behind the highlight above. Two things break and only one of them is a compile error.

A record pattern naming the original three components stops compiling, and the recipe appends the fourth binding for you.

An assertion comparing a whole record, `assertThat(result).isEqualTo(new WriteResult(streamId, 0, 1))`, still compiles. It now fails when it runs, because a new append id is created for every write that persists something, and nothing at build time points at it. No recipe can reach it either, since the expected append id is a value your source never states. Assert on the components you actually mean instead. [Section 6 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#6-writeresult-and-dcbappendresult-gain-a-fourth-component-the-append-id) has the before and after.

### `DurableSubscriptionModel` refuses a first subscription when no start position can be recorded

`DurableSubscriptionModel.subscribe(..)` now throws `IllegalStateException` when you ask for the default start position, no checkpoint is stored for the subscription id, and the wrapped model cannot say where the feed is. Both MongoDB models answer that way when the server refuses the `hostInfo` command, which shared Atlas clusters (M0, Flex and similar tiers) do. In a Spring Boot application it comes out as a startup failure.

The old behavior was that such a subscription started anyway from wherever the feed happened to be, with nothing recorded, so a crash before the first checkpoint was saved never came back to the event whose delivery had just failed. The refusal replaces that quiet loss with an error.

Three ways out. Set `occurrent.subscription.start-when-no-start-position-can-be-recorded=true` and you get the old behavior, chosen deliberately this time. Run against a tier that permits `hostInfo`, which on Atlas means M10 and up, and the subscription records its start position before anything is delivered. Or subscribe with a `StartAt` of your own. [Section 7 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#7-durablesubscriptionmodel-refuses-a-first-subscription-when-no-start-position-can-be-recorded) covers what each one costs.

### A saga instance that keeps failing is quarantined

An event that a saga's `evolve`, its `react`, or its command dispatcher could not handle used to be retried without limit, wherever the subscription model offered it again. What that held up depended on what feeds the subscription. Now a saga instance that has kept failing for five minutes, the default `SagaRunnerConfig.quarantineAfter`, can be quarantined, and the subscription moves on past it.

Only a subscription model that keeps the history it delivers can quarantine, which it says by implementing `HistoryRetainingSubscriptions`. Both MongoDB subscription models do. A saga on a bare `PushSubscriptionModel` or on `CatchupThenPushSubscriptionModel` gets no quarantine and keeps the 0.33.0 behavior.

Five things break with it. `SagaStatus.QUARANTINED` is a new constant, so an exhaustive `switch` or `when` over `SagaStatus` stops compiling. `SagaInstance` gains `failure()`, `SagaEnvelope` gains a `started` and a `failure` component, and `SagaRunnerConfig` gains `quarantineAfter`, each of which breaks a store, an implementation, or a record pattern written against 0.33.0.

The fifth breaks nothing at compile time. `findByStatus(ACTIVE, ...)` no longer returns a quarantined instance, so a stuck-instance check built on it now misses the instances that have stopped for good. Enumerate `QUARANTINED` as well. There is no recipe for any of the five. [Section 8 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#8-a-saga-instance-that-keeps-failing-is-quarantined-and-four-saga-types-change-with-it) has the code, and [the documentation](/documentation#saga-quarantined-instances) covers what to do with a quarantined instance.

### A reactor catch-up subscription can deliver a concurrent write twice

A reactor catch-up subscription now delivers an event a second time when a write that was still in flight during the replay was read by a history window. The replay used to put every id it read into the cache the live delivery filters against, so the change stream's own delivery of that event was dropped. The history reads now fill no cache, which is what all three blocking paths already did.

This is `ReactorStreamCatchupSubscriptionModel`, `ReactorDcbCatchupSubscriptionModel`, and `ReactorCatchupSubscriptionModel`, which routes to them. The blocking catch-up models are unchanged. On a single-primary MongoDB, a store with nothing being written during the replay sees no repeats at all.

Catch-up delivery on these models has always been at-least-once, so a handler that already tolerates a repeat needs no change. If yours increments a counter or writes an unconditional insert, make it safe before you upgrade, usually by keying the work on the CloudEvent id. `handoverCacheSize` now sizes the reconciliation overlap alone rather than the whole replay, so a value you raised for a large rebuild is bigger than it needs to be. [Section 9 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#9-a-reactor-catch-up-subscription-can-deliver-a-concurrent-write-twice) covers the deployments where the repeats reach further back than concurrent writes.

### Events `updateEvent` damaged before 0.34.0 need a one-off repair

This is stored data rather than code, and it reaches you only if your application called `EventStoreOperations.updateEvent` while running 0.33.0 or earlier. That write path stored `position` as a string instead of a number and dropped the indexed `dcbTags` array. 0.34.0 fixes the write path. It does not repair events that are already stored.

MongoDB compares values within a type, so a string `position` matches neither end of a numeric range. A damaged event is missing from DCB reads, from `exists` and `count`, from position-ordered stream reads, from position-based catch-up, and from the conflict query behind a conditional append, where it means an append that should have been refused is accepted. Nothing raises an error at any point. The position half of this hits a store with stream position enabled even if it never used DCB.

From 0.34.0 a store that writes position runs the check when it starts and warns when it finds something. A store that writes no position skips that check by default, so run the query in the upgrade guide yourself there. Run the `occurrent-eventstore-mongodb-update-event-repair` module to fix what it finds. Read [section 10 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#10-events-updateevent-damaged-before-0340-need-a-one-off-repair) first, because there are five cases the repair reports instead of restoring.

### A subscription handler Spring cannot invoke now fails startup

This only happens in the Spring Boot integration. A `@Subscription`, `@StreamSubscription`, `@DcbSubscription` or `@SynchronousSubscription` method that Spring's proxy cannot invoke now fails startup with `SubscriptionHandlerNotInvocableException`. It used to run on the raw bean instead, silently skipping `@Transactional` and any other advice. A private or final method behind a CGLIB proxy, a method declared only on the concrete class behind a JDK interface proxy, and any static method all fail this way.

Those four annotations also register their handlers later now, once every singleton has been created, the same phase `@Projection`, `@Snapshot` and `@Saga` already use. So a subscription at `StartPosition.NOW`, and every `@SynchronousSubscription`, never sees an event a bean writes while it is being created, from `@PostConstruct` for example. Move such a write to an `ApplicationRunner`, or start the subscription at `StartPosition.BEGINNING`. [Section 11 of the upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md#11-a-subscription-handler-spring-cannot-invoke-now-fails-startup-and-a-live-subscription-can-miss-a-startup-write) has the rest.

Full details are in the [changelog](https://github.com/johanhaleby/occurrent/blob/main/changelog.md), and the [upgrade guide](https://github.com/johanhaleby/occurrent/blob/main/doc/migration/upgrading-to-0.34.0.md) walks through every change with the by-hand translation where the recipe cannot reach.
